# Инструкции для разработки Markpad

## Назначение и исходные требования

Markpad — редактор Markdown на C++ для создания многостраничных документов. README и UI sketch задают следующие пользовательские возможности:

- Три редактируемых режима одного GFM-документа: исходник Markdown, WYSIWYG с непрерывной раскладкой и WYSIWYG с постраничной раскладкой. Отдельного режима read-only preview нет.
- Создание и редактирование многостраничных документов в стиле Word/WordPad.
- Подсветка синтаксиса.
- Открытие и сохранение Markdown-файлов.
- Экспорт в PDF и HTML.
- Настройки разметки страницы, темы, параметров редактора и сочетаний клавиш.

Это исходные требования, а не подтверждение того, что функции уже реализованы. При изменении требований сначала актуализируйте README и соответствующие тесты.

## Архитектурное направление

- Предпочтительная отправная точка — модульное настольное приложение на C++. README не указывает сетевых функций или независимого серверного развёртывания, поэтому микросервисы и распределённая архитектура не обоснованы.
- Разделяйте модель документа и операции с ним, GFM-преобразование, файловый ввод-вывод, экспорт, настройки и пользовательский интерфейс. UI не должен владеть правилами преобразования и сохранения документов.
- Используйте общую модель документа для редактирования во всех режимах и для экспорта; избегайте отдельных несогласованных копий содержимого. Все три режима предназначены для редактирования.
- Изолируйте конкретные UI-, Markdown- и PDF/HTML-библиотеки за небольшими интерфейсами, если это оправдано существующим кодом. Не вводите абстракции без реальной необходимости.
- Поддерживайте корректное поведение при ошибках чтения, записи и экспорта: не сообщайте об успехе, если операция не завершилась.
- Обрабатывайте GFM, встроенный HTML и пути файлов как недоверенный ввод. Во всех WYSIWYG-режимах отключайте скрипты и активный контент. HTML-экспорт также не должен незаметно переносить исполняемый активный контент.
- Целевые платформы: Windows и Linux. Используйте Qt как UI-фреймворк, CMake как систему сборки и C++20 как стандарт языка. Проверяйте доступность выбранных Qt-модулей и зависимостей на обеих платформах.
- Библиотеки Markdown и PDF пока не выбраны: сравните подходящие варианты при реализации по совместимости с Windows/Linux, лицензии, сопровождению, качеству рендеринга и возможностям безопасного экспорта.
- Приложение предоставляет Markdown-режим и два редактируемых WYSIWYG-режима: непрерывный и с автоматической раскладкой по страницам. Пагинированный режим и PDF-экспорт используют согласованные правила страниц.
- Диалект документа — GitHub Flavored Markdown (GFM). Не добавляйте инструменты форматирования, результат которых нельзя представить в GFM; таблицы и зачёркивание поддерживаются как расширения GFM, Underline не поддерживается.
- Пользовательские настройки хранятся в конфигурационном файле приложения. Определите платформенно-подходящее расположение файла при реализации; отсутствие или повреждение файла не должно приводить к сбою приложения.

### Архитектурные решения и оставшиеся вопросы

**Решение:** развивать приложение как модульный монолит. Это соответствует описанному локальному редактору и упрощает согласованность документа между режимами редактирования.

**Почему:** в README нет требований к удалённым сервисам, совместному редактированию, масштабированию по узлам или отдельному развёртыванию компонентов.

**Зафиксированный стек:** Windows/Linux, Qt, CMake, C++20. Версия Qt, конкретные Markdown- и PDF-библиотеки и допустимые варианты/границы переноса сложных блоков остаются решениями для этапа обследования и реализации. Не заменяйте уже принятые проектом решения без отдельного обоснования.

**SDI:** одно окно приложения отображает один документ; несколько открытых документов размещаются в отдельных окнах. Подробные границы компонентов, потоки данных, правила окон и открытые решения описаны в [ARCHITECTURE.md](./ARCHITECTURE.md).

**Среда разработки:** основной проверенный локальный профиль — Windows 11 + MSYS2 UCRT64, GCC 16.2.0, Qt 6.11.2, CMake 4.4.3, Ninja 1.13.2. Использовать UCRT64 GCC/Qt библиотеки вместе; не смешивать их с MSYS/CLANG64. Тесты — Qt Test под CTest. Целевые CI профили: Windows MSYS2 UCRT64 и Ubuntu/GCC; Linux workflow пока не запускался. `clang-format` обязателен для форматирования, `clang-tidy` — дополнительная проверка. PDF в первую очередь исследовать через Qt PrintSupport/QPdfWriter. Не устанавливайте отдельный HTML/PDF движок без архитектурного обоснования.

MSYS2 пакет `cmark-gfm` в текущем каталоге пакетов не найден; доступный пакет `cmark` реализует CommonMark и сам по себе не удовлетворяет требованию GFM. До фиксации Markdown-зависимости выполнить технический spike: проверить доступность/сборку GFM-парсера для UCRT64 и Linux, сохранение исходной структуры при parse-edit-serialize и лицензию. Не подменять GFM на CommonMark незаметно.

## План разработки

1. **Обследование проекта и фиксация требований.** Определить текущую структуру, сборку, версии Qt и принятые зависимости. Подтвердить CMake-сборку под Windows/Linux; выбрать библиотеки Markdown/PDF после проверки лицензий, поддержки платформ и качества рендеринга. Уточнить правила переноса сложных блоков.
2. **Основа приложения и модель документа.** Настроить воспроизводимую сборку CMake для C++20 и тестирование; определить модель Markdown-документа и основные операции открытия/изменения/сохранения.
3. **Режимы редактирования.** Реализовать редактирование GFM-исходника и два редактируемых WYSIWYG-режима. Проверить переключение режимов, сохранение семантики документа, подсветку синтаксиса и обработку некорректного GFM.
4. **Многостраничная компоновка.** Добавить автоматическую раскладку документа по страницам с учётом размера бумаги и полей. Зафиксировать правила разбиения и проверить длинные блоки, изображения, таблицы и переходы между страницами.
5. **Надёжный файловый ввод-вывод.** Реализовать открытие и сохранение Markdown, включая обработку ошибок, кодировки и подтверждение возможной потери несохранённых изменений согласно UX проекта.
6. **Экспорт.** Добавить HTML- и PDF-экспорт с проверкой результата, ошибок и согласованности PDF с пагинированным режимом. Не считать экспорт успешным, если файл не создан корректно.
7. **Настройки и завершение UX.** Реализовать темы, параметры редактора и сочетания клавиш; хранить их в конфигурационном файле приложения и определить безопасное поведение при отсутствующих/повреждённых значениях.
8. **Стабилизация и выпуск.** Проверить сценарии полного цикла, доступность/удобство ключевых действий и работу на заявленных ОС; подготовить инструкции сборки, тестирования и выпуска.

Этапы можно выполнять параллельно только после согласования контрактов общей модели документа и целевых платформ.

## Требования к изменениям

- Перед изменениями изучите относящиеся к задаче исходники, тесты, конфигурацию сборки и существующие соглашения. README может отставать от реализации.
- Делайте небольшие, целевые изменения; не добавляйте зависимости, платформенные допущения или публичные интерфейсы без необходимости и обоснования.
- Сохраняйте совместимость существующих файлов и поведения. Если формат или поведение меняется намеренно, документируйте изменение и его последствия.
- Для новой логики добавляйте соответствующие автоматические тесты. Особое внимание уделяйте граничным случаям парсинга, файловым ошибкам, настройкам страницы и экспорту.
- Явно обрабатывайте ошибки пользовательских операций; не скрывайте сбои и не подменяйте их успешным результатом.
- Документацию по пользовательскому поведению обновляйте вместе с реализацией.

## Ограничения и решения, не заданные README

- README не определяет версии Qt и зависимостей, поддержку/поведение сложных разрывов страниц, точные форматы обмена или расположение конфигурационного файла. Не выдавайте предположения за требования.
- README и sketch не задают совместное редактирование, облачную синхронизацию, сетевую работу, плагины или импорт иных форматов. Не добавляйте их в объём работ без запроса. Sketch включает настройку Auto Save; её поведение требуется определить до реализации.
- Не фиксируйте команды сборки/тестирования заранее: сначала используйте конфигурацию и инструменты, принятые в репозитории. Если их нет, согласуйте и добавьте минимальную воспроизводимую основу.

## Агентная команда и выбранные навыки

Агент-координатор (ведущий разработчик) отвечает за требования, распределение задач, интеграцию изменений и итоговые проверки. Он подключает специализированные роли по необходимости; не нужно запускать все роли для каждой задачи.

| Роль | Навык/агент | Ответственность |
|---|---|---|
| Архитектор / координатор | `architect` | Уточнить критерии приёмки, границы модулей, контракты и архитектурные решения; разбить работу, подготовить постановку задачи для AI prompt engineer и интегрировать результат. |
| Инженер промптов | `ai-prompt-engineer` | Преобразовать постановку архитектора в однозначный исполнимый промпт с контекстом, ограничениями, критериями успеха и форматом отчёта; выявить пробелы, влияющие на надёжность. |
| Разработчик C++ | `cpp-developer` | Реализовывать кроссплатформенную логику C++/Qt и устранять дефекты с учётом целевых Windows и Linux. |
| Автор тестов | `test-writer` | Подготовить сценарии и автоматические тесты после согласования контрактов; охватить обычные случаи, ошибки и граничные условия. |
| Сборка и CI | `devops-engineer` | Настраивать воспроизводимую сборку CMake, CI и проверки на Windows/Linux после появления проекта и требований к выпуску. |
| Технический редактор | `technical-documentation-specialist` — по необходимости | Согласовать README и пользовательскую/разработческую документацию с реализованным поведением. |

## Пайплайн разработки с агентами

1. **Триаж — координатор (`architect`).** Изучить относящиеся к задаче код, README, AGENTS.md, сборку и тесты; определить цель, область изменений, затронутые модули, ограничения, зависимости и открытые вопросы. Сначала разрешить решения, влияющие на публичные контракты или формат документа.
2. **Постановка и регистрация — координатор (`architect`).** Создать документ задачи в `docs/tasks/task_<NNN>.md` (например, `task_001.md`) до передачи реализации. Выбрать следующий свободный последовательный номер из существующих файлов; не перезаписывать и не перенумеровывать ранее созданные задачи. В документе зафиксировать контекст/проблему, цель, границы (включено и исключено), требования и ограничения, затронутые области, критерии приёмки, план проверок, зависимости и оставшиеся вопросы. Явно пометить предположения и неизвестные данные.
3. **Подготовка исполнительского промпта — `ai-prompt-engineer`.** Передать инженеру промптов содержимое постановки архитектора и только релевантный кодовый/проектный контекст. Инженер формирует отдельный точный промпт для исполнителя: роль и цель, допустимая область изменений, необходимые исходные сведения, обязательное поведение, критерии приёмки, тесты/команды проверки, ограничения безопасности, формат итогового отчёта и правила поведения при недостающих требованиях (остановиться и запросить уточнение, не выдумывать требования). Итоговый промпт и обнаруженные неоднозначности записать в тот же `task_<NNN>.md`; существенные пробелы вернуть архитектору до начала реализации.
4. **Проектирование и реализация — координатор и `cpp-developer` (или другая профильная роль из списка навыков).** Архитектор утверждает границы и контракты, затем исполнитель работает по согласованному промпту в существующей структуре. Сравнение внешних библиотек поручать отдельно только при наличии реального выбора, проверяя лицензии, платформенную поддержку и сопровождение. Несвязанные задачи можно выполнять параллельно только после фиксации общих интерфейсов и владения файлами.
5. **Тестирование — `test-writer` и исполнитель тестов.** Подготовить или обновить автоматические тесты для критериев приёмки и ошибок. Разработчик запускает доступные целевые тесты, сборку и статические проверки; CI/исполнитель проверяет обе ОС, когда соответствующие конфигурации доступны. При дефекте результат возвращается исполнителю с воспроизводимыми шагами и ожидаемым поведением.
6. **Проверка изменений — координатор.** Просмотреть итоговый diff на корректность, регрессии и обработку ошибок. Для Markdown/HTML, путей, файлового ввода-вывода и внешних зависимостей отдельно проверить границы безопасности. Если нужен независимый аудит, сначала убедиться, что в текущей среде доступен соответствующий инструмент или специалист; не считать такую проверку выполненной без фактического запуска.
7. **Документация, интеграция и приёмка — координатор, `technical-documentation-specialist` по необходимости.** Обновить README/документацию и task-документ (итог реализации, выполненные проверки, отклонения и оставшиеся риски), интегрировать только проверенные изменения и сообщить результат.

### Правила взаимодействия и контрольные точки

- Координатор остаётся ответственным за единое решение и приёмку; специализированные агенты возвращают краткий результат, список изменённых файлов, проверки и открытые риски.
- Для каждой планируемой задачи разработки обязателен task-файл `docs/tasks/task_<NNN>.md` и handoff «архитектор → AI prompt engineer → исполнитель». Архитектор отвечает за правильность требований; prompt engineer — за ясность и проверяемость исполнительского промпта. Промпт не может расширять или менять постановку архитектора.
- В task-файле отделять исходные требования, решения/предположения, финальный промпт и отчёт о выполнении. Перед запуском реализации статус задачи должен быть `Ready`; при существенной неоднозначности оставлять её `Draft` и возвращать архитектору.
- Task-файл должен содержать заголовки: `Статус и владелец`, `Контекст`, `Цель`, `Область работ`, `Ограничения и предположения`, `Критерии приёмки`, `План проверок`, `Зависимости и открытые вопросы`, `Исполнительский промпт`, `Итог выполнения`. В исполнительском промпте явно задавать цель, входной контекст, область/запреты, проверяемый результат, проверки, формат отчёта и поведение при блокерах. Статус использовать из набора `Draft`, `Ready`, `In Progress`, `Blocked`, `Done`; неизвестные значения и незапущенные проверки обозначать явно.
- Каждый исполнитель получает ограниченную задачу с явными критериями завершения. Не поручать нескольким агентам один и тот же поиск/изменение и не считать предложения агента выполненными до проверки.
- Параллелить только независимые задачи. Проектирование API, общая модель документа и интеграция должны иметь одного ответственного; сначала согласовать контракты, затем делить работу.
- До интеграции должны пройти релевантные тесты и сборка. Для изменений поведения — обновить тесты и документацию; риски безопасности, которые нельзя устранить или проверить, явно зафиксировать как блокирующие/оставшиеся.
- Применять только необходимые навыки: небольшой локальный дефект может пройти координатор → разработчик → целевая проверка; новая функция обычно требует разработчика и тестирования; изменения рендеринга/экспорта требуют усиленной проверки безопасности координатором.
- Не заявлять о выполнении проверок или аудитов, которые фактически не проводились. При отсутствии инструментария указать это как блокирующий или оставшийся пункт, а не заменять фиктивным успехом.

В проекте пока нет исходников и конфигурации CMake, поэтому команды сборки, тестирования и линтинга ещё не проверены. Каталог [docs/tasks/](./docs/tasks/README.md) содержит начальный backlog. При создании следующих задач использовать наименьший ещё не использованный последовательный номер; когда сборка появится, координатор должен проверить и внести точные команды и критерии CI для Windows и Linux.

### Начальный набор пакетов MSYS2 (устанавливается пользователем по необходимости)

Запускать в **MSYS2 UCRT64** после обновления пакетов (`pacman -Syu` и перезапуск терминала, если MSYS2 его потребует). Установка пакетов — действие владельца рабочей среды. Проверенная среда уже содержала GCC, CMake, Ninja и Qt 6; повторная установка не требуется, если они доступны:

```sh
pacman -S --needed base-devel mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja mingw-w64-ucrt-x86_64-qt6-base
```

В проекте запрашиваются Qt6 Widgets и Qt6 Test; Qt Designer/Linguist и PrintSupport не нужны для текущего минимального каркаса. Форматтер/анализатор Clang подключать отдельно после выбора проверенного источника бинарных инструментов; не смешивать случайные UCRT64 и CLANG64 библиотеки в одной сборке.

Проверенный локальный цикл в PowerShell (явно выбирает UCRT64 инструменты и Qt prefix):

```powershell
$env:PATH = "C:\msys64\ucrt64\bin;C:\msys64\usr\bin;$env:PATH"
& "C:\msys64\ucrt64\bin\cmake.exe" -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_PREFIX_PATH="C:\msys64\ucrt64"
& "C:\msys64\ucrt64\bin\cmake.exe" --build build --parallel
& "C:\msys64\ucrt64\bin\ctest.exe" --test-dir build --output-on-failure
```

UCRT64 `bin` должен быть в `PATH` и при запуске тестов, чтобы Windows нашёл Qt DLL. Локально проверено в MSYS2 UCRT64 с GCC 16.2.0, CMake 4.4.3, Ninja 1.13.2 и Qt 6.11.2: чистая конфигурация, сборка приложения/тестов и CTest проходят. Проверенная сборка использовала каталог `build-task001-qt`. Linux и GitHub Actions требуют отдельного CI-запуска. Полная инструкция с командами запуска приложения находится в [README.md](./README.md).
